# Личное облако «Как давно»

Первый этап: один аккаунт, общий проект Supabase `kladovaya`, облачные изменения только с интернетом.
Сайт остаётся статическим и может работать на GitHub Pages. Новые библиотеки не нужны.
Локальная история и облачная история независимы: вход и выход не перезаписывают локальные записи.

## 1. Выбери существующий аккаунт

Открой проект `kladovaya`. Для «Как давно» используй тот же email и пароль, с которыми входишь в приложение «Кладовая».
В Authentication → Users найди своего пользователя по email и скопируй его UUID — идентификатор, не пароль.
Не создавай нового пользователя. Если нужного email нет в списке, остановись: сначала нужно выяснить, как устроен вход в «Кладовую».

Не меняй настройки регистрации, провайдеров входа, URL перенаправления и почты: они общие с «Кладовой».
Форм регистрации и восстановления пароля в «Как давно» нет. Смена пароля этого аккаунта затронет оба приложения.
База, Auth и лимиты ресурсов общие. Таблицы `kd_*` и проверка владельца отделяют данные «Как давно»,
но не создают изолированный сервер. Права доступа к таблицам соседнего приложения этим кодом не проверяются и не меняются.

## 2. Создай таблицы и назначь владельца

Сначала в SQL Editor проекта `kladovaya` выполни только проверку существующих имён (она ничего не изменяет):

```sql
select 'relation' as kind, c.relname as name
from pg_catalog.pg_class c
join pg_catalog.pg_namespace n on n.oid = c.relnamespace
where n.nspname = 'public' and left(c.relname, 3) = 'kd_'
union all
select 'function', p.proname
from pg_catalog.pg_proc p
join pg_catalog.pg_namespace n on n.oid = p.pronamespace
where n.nspname = 'public' and left(p.proname, 3) = 'kd_';
```

Ожидаемый результат — ноль строк. Если строки есть, остановись: не удаляй объекты и не запускай установку повторно.
После проверки вставь весь `supabase/schema.sql` и выполни один раз.
Комментарий в начале SQL о новом проекте относится к исходному варианту установки: здесь требуется отсутствие объектов `kd_*`.
Скрипт не меняет таблицы «Кладовой» и настройки Auth; права назначаются только для объектов «Как давно».
Скрипт создаёт таблицы `kd_tasks` (дела), `kd_entries` (выполнения),
`kd_state` (версия и отметки переноса), `kd_owner` (единственный разрешённый аккаунт).
RLS включён; запись доступна только через функции с проверкой владельца и версии.

Затем отдельно выполни, заменив UUID:

```sql
insert into public.kd_owner (user_id)
values ('UUID-ТВОЕГО-ПОЛЬЗОВАТЕЛЯ');
```

Даже случайно созданный второй аккаунт не получит доступа. Не меняй владельца для обычного входа.
Не запускай schema.sql повторно поверх готовой базы: для следующих изменений потребуется отдельная миграция.

После установки, до переноса истории, выполни `supabase/verify.sql`: он проверяет ограничения доступа, атомарность,
конфликт версий и повторный перенос. В конце стоит `rollback`, поэтому тестовые записи не сохраняются.
При ошибке выполни `rollback;`, сохрани текст ошибки и не переходи к переносу реальной истории.
Этот SQL подготовлен для ручной проверки: агент не подключался к Supabase и не выполнял его.

## 3. Заполни публичную конфигурацию

В настройках проекта найди Project URL и **Publishable key** (`sb_publishable_...`).
Заполни только эти два значения в `supabase-config.js`:

```js
globalThis.KAK_DAVNO_SUPABASE = Object.freeze({
  url: 'https://PROJECT_REF.supabase.co',
  publishableKey: 'sb_publishable_ПУБЛИЧНЫЙ_КЛЮЧ',
});
```

Здесь поддерживается новый Publishable key, а не старый `anon` JWT.
Публичный ключ можно размещать в клиентском коде: доступ ограничивается Auth, RLS и проверкой владельца в RPC.
**Secret key, service_role, пароль пользователя и пароль БД сюда не вставлять.**
Конфигурацию вводи в файл самостоятельно; не присылай пароли в чат.

После настройки обнови номер `CACHE` в `sw.js`, чтобы установленное приложение получило новые файлы.
Проверь изменения и опубликуй сайт обычным для тебя способом. Агент не делает commit, push или deploy.

## 4. Войди и перенеси историю

1. Открой приложение на устройстве, где уже есть история, по прежнему адресу сайта.
2. Настройки → войди с email и паролем своего аккаунта «Кладовой». Откроется отдельная облачная история (сначала пустая).
3. Нажми «Перенести историю с этого устройства».
4. Скачай локальную копию, проверь сохранённый файл и отметь подтверждение.
5. Нажми «Подтвердить перенос в облако». Дождись сообщения об успехе.
6. На втором устройстве открой тот же сайт, войди тем же аккаунтом. История загрузится из облака.

Перенос объединяет записи по идентификаторам. Совпадающие идентификаторы с разным содержимым
останавливают перенос без изменения данных. Настройки уже существующих облачных дел сохраняются.
Отметка переноса хранится в базе: повторный перенос с этого браузера не восстановит удалённые облачные записи.
Очистка данных браузера удаляет идентификатор источника; после неё не переноси старую локальную копию повторно без необходимости.
Последующие изменения в локальном режиме сами в облако не попадут.

## Как работает первый этап

- В облаке сохранение подтверждается только после ответа Supabase. До этого интерфейс блокирует второе действие.
- При отсутствии ответа нельзя знать, успел ли сервер сохранить запрос. Приложение откатывает отображаемое изменение
  и требует «Загрузить из облака» перед следующим сохранением. Автоматического повтора записи нет.
- Если другое устройство успело сохранить данные, устаревшая версия отклоняется. Загрузи свежую историю и повтори действие.
- При открытии вкладки и возвращении в неё данные загружаются, если окно редактирования закрыто.
  Для двух постоянно открытых устройств есть кнопка «Загрузить из облака». Realtime и очередь офлайн-изменений не добавлены.
- Облачная история не записывается в локальную историю и не кэшируется service worker.
  Уже открытый список можно читать при потере связи, но после закрытия вкладки для загрузки понадобится интернет.
- Сессия хранится в `localStorage` и восстанавливается после закрытия приложения; пароль не сохраняется.
  Истёкший access token обновляется через refresh token. В браузерах с Web Locks обновление согласуется между вкладками.
  После обновления со старой версии потребуется один раз войти заново. Очистка данных сайта или отзыв сессии потребуют нового входа.
  Если браузер запрещает хранение данных, вход сохраняется только в памяти до перезапуска.
- Выход очищает сессию на устройстве даже при сбое сети и возвращает локальную историю.
- Для небольшого личного журнала сохраняется полный снимок в одной транзакции, со стабильными ID дел.
  Лимит одного снимка: 20 000 выполнений и 5 МБ JSON. Масштабирование — отдельный этап.
- Экспорт/импорт файла относится к выбранному режиму. Сохраняй резервные копии и облачной истории.

## Проверки без подключения к базе

```powershell
node --test tests/*.test.cjs
node --check cloud.js
node --check sw.js
```

HTTP-тесты используют подменённый `fetch`, а не реальный Supabase. SQL-проверки выполняются отдельно вручную.
Для локального просмотра: `node tests/preview.cjs`, затем открой `http://127.0.0.1:4173`.
Для проверки интерфейса с имитацией облака: `node tests/preview.cjs --mock-cloud`, адрес `http://127.0.0.1:4174`.
На тестовом стенде используй email `test@example.test` и любой выдуманный пароль. Настоящие данные входа там не нужны.
Облачные данные стенда живут только в памяти процесса; это не проверка реального Supabase или RLS. Остановка — Ctrl+C.
Перед переносом истории проверь: вход владельца; отказ другому аккаунту; добавление, переименование, архив,
удаление и отмену; загрузку на втором устройстве; конфликт двух вкладок; отказ сохранения без сети; выход в локальный режим.
